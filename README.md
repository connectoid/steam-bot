# Steam Top-up Bot (Payli / СБП)

Telegram-бот: пользователь один раз вводит логин Steam, дальше просто присылает
сумму — бот создаёт заказ в Payli, присылает ссылку/QR на оплату по СБП и
уведомляет о результате зачисления.

## Как это устроено

- `config.py` — все настройки читаются из `.env`.
- `db.py` — SQLite: логины пользователей, заказы, дедупликация вебхуков.
- `payli_client.py` — обёртка над Payli Partner API (`services`, `orders`).
- `bot.py` — хендлеры Telegram (aiogram 3) + отдельный aiohttp-сервер,
  который принимает вебхуки Payli на `/payli/webhook` и шлёт пользователю
  уведомление о финальном статусе заказа.

## Запуск (локально, для теста)

```bash
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# заполните .env реальными значениями
python bot.py
```

Для локального теста вебхуков понадобится туннель наружу (ngrok/cloudflared),
так как Payli требует публичный HTTPS-адрес.

## Деплой

Рекомендую разворачивать на VPS (а не на локальной машине), особенно с учётом
спутникового интернета — бот должен быть доступен 24/7 и отвечать на вебхуки
без задержек спутникового канала.

Типичная схема:
1. VPS с белым IP.
2. Nginx как реверс-прокси с TLS (Let's Encrypt/certbot) на 443 порту,
   проксирующий `/payli/webhook` на `127.0.0.1:8443` (или другой `WEBHOOK_LISTEN_PORT`).
3. `WEBHOOK_PUBLIC_URL=https://ваш-домен/payli/webhook` — именно этот адрес
   передаётся в заказ и именно на него будут приходить уведомления.
4. Процесс бота держите под systemd или supervisor, чтобы он перезапускался
   при падении.

Требования Payli к `webhook_url` (из документации): только `https`, порт 443
или 8443, публичный хост (приватные/локальные адреса отклоняются) — это уже
учтено в схеме выше.

## Как считается сумма к оплате

Пользователь присылает сумму, которая должна **зачислиться** на Steam.
Payli берёт комиссию из суммы платежа, а не сверх неё:

```
credited_rub = amount_pay_rub × (1 − total_commission_percent / 100)
```

где `total_commission_percent = base_commission_percent (Payli) + MARKUP_PERCENT (ваш)`.

Бот решает обратную задачу — по желаемой `credited_rub` считает, сколько
нужно `amount_pay_rub`, и именно эту сумму показывает пользователю к оплате.
`base_commission_percent` запрашивается у Payli динамически (`GET /services`)
перед каждым заказом — он может меняться, поэтому в коде не захардкожен.

Ваша наценка `MARKUP_PERCENT` задаётся в `.env`. Из неё Payli также удерживает
свою долю (`partner_commission_share_percent` — видно в ответе на заказ);
процент вашей доли настраивается в личном кабинете Payli, бот его не трогает.

## QR-код

API Payli возвращает `payment.pay_url` — ссылку на страницу оплаты, а не
готовое изображение QR для прямого сканирования банковским приложением.
Бот сам генерирует QR-код, кодирующий эту ссылку (удобно, если пользователь
сидит за компьютером и хочет открыть оплату на телефоне). Основной способ
оплаты — кнопка «Оплатить по СБП» со ссылкой на `pay_url`; на самой странице
оплаты уже будет показан настоящий QR для СБП или произойдёт переход в банк.

## Что ещё стоит доделать перед продакшеном

Это рабочий скелет, а не продакшен-готовый код. Перед реальным запуском
советую добавить:

- **Обработку сетевых ошибок/таймаутов** при создании заказа — сейчас при
  сбое пользователь просто получает сообщение об ошибке; стоит добавить
  повтор с тем же `idempotency_key` (как рекомендует документация для
  `502 provider_bad_response` / `payment_url_missing`).
- **Опрос статуса как резерв**, если вебхук не дошёл (документация
  гарантирует до ~8 попыток в течение часа, но не бесконечно) — можно
  раз в несколько минут проверять зависшие `pending_payment`-заказы через
  `GET /orders/{public_id}`.
- **Уведомление администратора** (вас) при статусах `failed` / `chargeback` —
  чтобы оперативно реагировать на спорные случаи, а не только пользователю.
- **Лимиты запросов** — учитывайте `GET — 600/мин, POST — 60/мин` на токен,
  при росте нагрузки может понадобиться своя очередь.
- **Логирование заказов для бухгалтерии** — сейчас в SQLite хранится
  минимум; для сверки с выводом средств удобно дублировать сырые ответы
  Payli (например, в отдельную таблицу `order_events`).
- Проверить баланс партнёра (`GET /balance`) перед стартом продаж и
  настроить алерт на низкий баланс — без средств на балансе создание
  заказов может начать падать.

## Тестирование

1. Проверьте `/start` → ввод логина → валидация.
2. Пришлите сумму в пределах `min_rub`–`max_rub` (сейчас это берётся из
   ответа `/services`, в документации пример — 100–15000 ₽ для Steam).
3. Оплатите тестовый заказ на небольшую сумму и убедитесь, что вебхук
   приходит и бот присылает финальное уведомление.
4. Проверьте сценарий неверного логина — Payli вернёт `400 steam_login_invalid`
   на этапе создания заказа.
